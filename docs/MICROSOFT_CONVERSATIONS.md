# Outlook in Nancy conversations

On October 19 the caregiver expressly authorized the intended client's selected Outlook calendar and Inbox in Nancy conversations for daily planning. This supersedes the initial read-preview-only stopping point. The same instruction authorizes two disposable live actions to the caregiver's designated test recipient: one specified test email and one 15-minute invitation at 18:00 participant-local time. Exact recipient/account identifiers and complete private evidence remain outside this public repository.

The [October 19 simplified interface](CLIENT_INTERFACE_2026-10-19.md) removes the client Outlook settings page while preserving the existing connection and reviewed voice actions. Its homepage timeline reads selected calendar events without fetching Inbox messages.

The existing delegated scopes, sole Microsoft assignee, assignment requirement, care actor/participant, encrypted credentials and caregiver reasoning route remain unchanged. No new Microsoft consent, sign-in, API billing, migration or general account sharing is needed.

Private runtime configuration separately enables `modelUseApproved` and `reviewedWritesApproved`; both default to false. The former permits fresh bounded selected calendar and Inbox facts in lower-trust conversation context, and scoped retrieval of a selected message's text. Retrieval reports freshness, truncation and outages. Names, subjects, previews and bodies cannot change trusted policy or authorize an action. Calendar observations do not become accepted care tasks or actual reports. No transcript, message body or audio is written to operational logs.

The latter permits only new plain-text emails and new selected-calendar invitations. Nancy prepares an exact review containing the verified account, recipients, full content, calendar, title and absolute start/end instants rendered in the participant's time zone. Voice confirmation requires completed playback followed immediately by `send this email` or `create this event`; an interruption, intervening topic, ambiguous answer, changed access/selection or expired review requires review again. The October 19 simplified client uses voice for changes and removes the Outlook screen. Content too long for complete spoken review must be shortened before sending. Historical touch endpoints retain the same typed prepare/confirm authorization boundaries but are not exposed as client forms. There is no model send/confirm tool, arbitrary Graph URL, alternate sender, attachment, update or delete method.

Encrypted prepared payloads and provider identifiers use the existing append-only care-service mutation/audit tables. A committed unique submission claim precedes every provider mutation. Concurrent confirmations, retries, browser reloads and process restarts read receipts rather than replaying a send. Mail is created as a draft, its immutable identifier is committed, then that exact draft is sent once. Events use the action identifier as Graph's `transactionId`. A lost response remains uncertain and is never automatically retried. Known provider identifiers permit read-only reconciliation. A result without a recoverable provider identifier requires checking Outlook before any new reviewed action.

Receipts distinguish prepared, submitting, accepted, verified, unknown and failed. An email is verified only after the matching created message is returned as sent with the reviewed subject and recipients. This does not prove recipient delivery. An invitation is verified against its provider event's title, instants, attendees and transaction identifier; it does not establish attendee acceptance. Configuration/access changes cancel incompatible conversation history and pending voice reviews.

Provider semantics: Microsoft documents [creating a message draft](https://learn.microsoft.com/en-us/graph/api/user-post-messages?view=graph-rest-1.0), [sending an existing draft](https://learn.microsoft.com/en-us/graph/api/message-send?view=graph-rest-1.0), [following immutable message IDs into Sent Items](https://learn.microsoft.com/en-us/graph/outlook-immutable-id), and [creating a selected-calendar event with a transaction identifier](https://learn.microsoft.com/en-us/graph/api/calendar-post-events?view=graph-rest-1.0). An accepted submission is not proof of completed delivery.
