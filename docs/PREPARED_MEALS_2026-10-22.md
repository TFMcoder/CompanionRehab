# Owner test: meal recommendations prepared before a conversation

The October 22 owner direction authorizes preparation in the separate synthetic test copy, with the existing Pro connection, pinned Heart voice and Dad’s runtime unchanged. This is an experimental engineering checkpoint within S01. It does not complete intended-person/device, clinical, genuine-day or full-slice acceptance.

## Behavior and boundaries

The private startup selection adds `meal_mode: ahead-v1` to the existing exact owner Sol-low/prepared/Heart/quick-read/spoken trial. The default remains off. Main does not read that selection. On an authenticated foreground page load, the enabled service prepares one breakfast/lunch/dinner draft using the same bounded Nancy reasoner. No recurring preparation job, new account route, API key, new provider option or paid service is introduced.

One no-tool model request selects only matching-category repository IDs. The server validates the JSON schema, IDs and conservative known food exclusions. Incomplete or conflicting choices remain unavailable. It renders source titles and a short explanation from actual ingredient groups, then prepares exact first-part Heart audio for the three single-meal variants and the combined menu. No model-generated clinical numbers or safety claims enter the rendered draft. These are general ideas from unreviewed repository material, not a prescribed diet, approved meal, actual intake report, product-label check or allergy clearance.

The draft and audio remain in memory. Its key covers the authenticated login/actor/client/role/grants/policy/account binding, participant-local date, profile, confirmed preferences, meal/check-in/intake/ledger facts, active handoffs and source hashes/material. It expires after ten minutes. Scope and food facts are rechecked before a reply, turn retry and speech delivery. Logout, scope failure, expiry and service close discard work. Repeated page requests deduplicate; an active conversation cancels and drains unfinished preparation before using the same reasoner. Cancelling an overlapping ready-cache validation preserves the already completed draft owned by the earlier job. There are no automatic provider retries. The trial allows at most four preparation attempts per process, at least ten minutes apart, including failed or aborted attempts. That cap resets on a deliberate process restart; it is not a durable daily allowance.

Only a narrow, neutral meal-idea question on the first user turn can use the draft. New dietary constraints, other dates, alternatives, quantities, safety questions, actions, later turns and unrelated conversation use the existing path. A prepared draft is consumed once. This conservative scope prevents a generic recommendation from discarding spoken context; it also means this experiment does not accelerate every meal conversation. If the page has not finished preparation, the question uses the normal path.

Preparation has a separate numeric telemetry stage and provider-reported usage; unknown usage remains null. Ready-answer turns record zero model calls and a prepared-meal hit. The bounded diagnostic label passes the existing privacy whitelist. Transcripts, drafts, audio and credentials are not persisted in runtime diagnostics or public evidence.

Preparation time is excluded from question-to-first-audio time and reported separately. The endpoint is a valid first audio buffer available to the server/test harness; this is not a measured Safari microphone-to-ear delay.
