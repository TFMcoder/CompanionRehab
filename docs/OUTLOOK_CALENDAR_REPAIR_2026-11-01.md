## Separate registration requirement

Microsoft documents that consent persists across application runs: a token can contain previously consented scopes for the resource even when the new request asks for fewer. Its independent architecture guidance describes the same cumulative behavior. Requesting only shared-calendar read scopes through the primary app is therefore not an isolation boundary. [Microsoft consent lifetime](https://learn.microsoft.com/en-us/entra/msal/javascript/browser/resources-and-scopes#consent-lifetime), [Microsoft authorization guidance](https://learn.microsoft.com/en-us/entra/architecture/authorize-applications-resources-workloads)

For this implementation, a secondary token containing the primary app's Mail/Write scopes would correctly fail the strict read-only validator. Adding shared-read consent to the primary app could also cause its next token refresh to fail on the newly returned unexpected scope, triggering reconnect-required cleanup. **Do not add the new shared scope to the primary app, reuse the old same-app proposal or relax either scope whitelist.** Synthetic tokens containing only requested scopes did not establish real-provider compatibility.
